# Codex Mockup-First Design

Use this workflow for new visual designs and redesigns. The goal is faithful implementation of a complete visual target, not improvising a different site while coding. Existing content-only edits and nonvisual repairs remain bounded to their requested change.

## Establish Every Screen Before Building

For reusable themes, first complete [the early native design proof](early-design-proof.md) after concept selection. Its isolated home/article/menu fixture is the sole limited exception to the before-implementation rules below. Resolve its seven decisions and scoped review before full screen generation; the complete screen inventory and mockup review still precede production theme implementation.

Inventory every requested page, route, and visibly distinct state. Include search results and no-results, 404, and open mobile navigation when those are in scope. Generate a desktop and mobile mockup for every screen before production implementation, except for the limited early native proof described above. For states that only exist at one viewport, such as a mobile-only navigation overlay, generate that state at its actual viewport and mark the other as not applicable; do not invent a desktop overlay. Cover the entire page, including its footer, not only the hero. Long pages may use clearly ordered continuation images with consistent width and shared elements.

For repeated content, one representative mockup can cover the exact same template only when the inventory explicitly maps every affected route to it. A materially different layout or state needs its own image. Do not silently use the homepage as the design for archives, articles, and utility pages. An isolated pattern needs only its own desktop and mobile compositions, not an invented full site. Do not mock up WordPress admin screens unless those interfaces are actually being redesigned.

Inspect the current site, real copy, media, Global Styles, and installed Canvas capabilities before prompting. Preserve the existing identity unless the user requested a new one. For a new theme, choose a coherent visual system first; for existing-site work, derive it from the site. The mockups must use that system, so faithful implementation does not conflict with inherited typography or colors.

## Make Personality Belong To The Theme

### Explore With A Purpose

Apply [the compelling-design gate](compelling-design.md): require an editorial premise expressed visibly through type, structure and reading/browsing rhythm, not only a distinctive illustration. Critique actual comparable concepts for memorable relationships and ordinary-content resilience. If none is convincing, revise the premise within budget rather than generating a full screen family by default.

Define a specific readership, publishing habit, and editorial purpose before prompting. Study a small diverse set of attributed primary design references when useful; record transferable type/composition principles rather than copying a visual identity. Judge a meaningful long-prose article, ordinary-media story, and text-only entry early in the selected direction, including phone reflow. Reading comfort and page rhythm should inform the design before spending on the complete screen inventory. Keep originality, usability, and craft judgments separate; an independent reviewer may conclude that none of the three directions is strong enough. Do not manufacture a winner.

For an open-ended new theme, generate exactly three materially different representative Imagegen concepts and present them as **Concept 1**, **Concept 2**, and **Concept 3**, each with a short name and rationale tied to the subject and reader. Use comparable content and viewport sizes. Vary the editorial structure, typographic relationships, reading rhythm, and navigation grammar, not just colors or decorative assets. Avoid claiming unprecedented originality without evidence. Respect the user's credit budget; do not generate every route for all three directions.

Ask the user to choose one of the three concepts before expanding it. This is an intentional direction-selection checkpoint: do not silently select a winner or treat a reviewer recommendation or general praise as the user's selection. Once selected, complete the early native proof, then use the concept and its proved shared components as references to generate desktop/mobile mockups for every distinct in-scope screen and state. Complete the inventory and Marge mockup review, repair material findings, and only then implement the actual native WordPress theme. Follow with the browser fidelity and Marge final-review checkpoints. If the user explicitly delegates selection, select and explain the direction yourself. An explicitly supplied direction, routine edit, or existing design does not need another three-concept round; a taste-only exercise remains within its commissioned scope.

Use the same realistic content across directions so stronger imagery or better copy cannot disguise a weaker system. Include ordinary unrelated images, varied aspect ratios, and a text-only story. Image-free output is an optional stress test, not the design brief unless requested. A theme may be richly image-led while retaining a recognizable supporting identity when its media changes.

Inspect actual outputs before praising or selecting them. Judge readability and usefulness separately from artistic appeal: an accessible composition can still be generic, and an expressive one can still be difficult to use. Name concrete distinguishing relationships, weak areas, and the most valuable correction. When independent review is requested, give the reviewer the brief and actual images without a preferred verdict; use Marge and installed Impeccable when available. Treat reviewer preference as evidence, not user approval.

Keep a compact record of direct user feedback, reviewer findings, and resulting revisions. Preserve the distinction between observations and hypotheses. Carry only supported lessons into reusable instructions; do not turn one rejection into a universal style ban. This is workflow and taste calibration, not retraining the model. After choosing a direction, complete the early native proof, then its screen inventory and mobile adaptations before production implementation. Do not substitute repeated promises for the next authorized action.

Make expressive details sustainable: annotation rails, folio numbers, and alternate story treatments should carry useful editorial information and work with native dynamic content. Optional annotations must not require a bespoke illustration or handwritten aside for every post. Keep long headlines on reliable reading surfaces; dramatic type must not spill across arbitrary replacement photos. Reserve condensed capitals for brief display text, and simplify tiny decorative metadata rather than shrinking it to fit. These are composition lessons, not a requirement to add rails or annotations to every design.

For reusable themes, separate the **theme system** from **editorial content** before generating polished screens. The theme system is the typography, color roles, layout relationships, spacing rhythm, navigation, recurring block treatments, and any bundled decorative assets. Editorial content is the replaceable photographs, illustrations, titles, and excerpts. Do not mistake a coordinated set of generated images for a distinctive theme.

Record a short identity contract: name three recognizable decisions that survive replacing all editorial images, and map each to an editable implementation surface. Examples are a particular masthead/type hierarchy, a recurring composition and spacing rhythm, and a consistent rule/color/control language. Three arbitrary decorations do not count; explain how the choices serve this subject and its readers. A logo and accent color alone are insufficient. Treat these as decisions for this theme, not a recipe every theme must copy.

Put shared tokens in `theme.json` and Global Styles; express recurring compositions through templates, template parts, patterns, and supported block styles. Canvas supplies editable placement and layering. Optional theme-owned textures, marks, and fonts may contribute personality if bundled with appropriate licensing, but must not masquerade as required post images. Prefer a few coherent structural choices over adding stamps, grain, borders, or rotated text to every surface. Keep reading text and controls clear. Use normal editable site branding; do not bake the demo publication's name into every template.

Direct the first representative mockup to show those structural decisions with ordinary, visually varied content, not only bespoke matching art. Establish that composition before commissioning a complete matching illustration set. An image-led portfolio can still be image-led: the goal is a recognizable and usable supporting system, not equal visual impact without its work. For an existing design, preserve the authorized identity rather than imposing a new one to satisfy this check.

Define media behavior as part of the design: landscape, portrait, and square uploads; light, dark, and visually busy images; missing featured images; and an archive mixing illustrated, photographed, and text-only posts. State when to crop, contain, or omit the media region. A missing image must yield a deliberate text-led composition, not an empty fixed-height frame or an unrelated stock substitute. Never depend on a particular image's pale corner for legible headline overlays. Use a reliable theme-owned treatment or move copy outside the image when replacement content makes it unreadable. Optional duotone or framing must remain editable and appropriate to the content; never force a destructive treatment on every upload merely to make the demo match.

Before delivery, run a bounded **content-swap test** on the representative home, archive, and article compositions at desktop and mobile:

1. Keep theme-owned styles, fonts, and decorative assets, but replace the curated editorial art with varied ordinary photos. Include different aspect ratios and an image with no safe space for overlaid copy.
2. Remove featured images using the genuine no-image data state, including a mixed archive. Merely hiding images with CSS is not proof that the template handles their absence.
3. Use short and long titles, realistic excerpts, and a different site title. Verify layout, reading order, contrast, crops, and navigation remain usable without hand-adjusting each post.

Use an authorized disposable fixture for changed content, never rewrite published posts or unsaved edits. Reuse available authorized test media; do not commission another illustration set just for this test. Compare screenshots in the same review batch, naming the identity decisions still visible in each state. Pass only when the theme remains recognizable beyond its logo, ordinary content looks intentionally presented, and missing media does not break the composition. If swapping images reduces it to a generic layout, revise the type/layout/block system rather than generating prettier replacement art. Report this result separately from mockup fidelity; mark it untested when no safe fixture is available. Small copy edits do not trigger a full content-swap audit.

## Use Codex Imagegen

For new themes, plan site-wide graphics alongside the selected identity, not only featured images and screen comps. Use built-in Imagegen for bespoke raster illustrations, theme-owned marks, textures, and recurring artwork when appropriate to the brief. Establish their role across routes in the mockups, then generate clean shipping assets separately with suitable transparency and inspect their actual desktop/mobile placement. Reuse shared assets, bundle source/license credits, keep placement editable, and separate theme-owned graphics from replaceable editorial media. Do not ship cropped mockups as assets, flatten typography or controls, or add decorative clutter merely to appear detailed. Familiar UI symbols remain native or use the existing icon library. Shared artwork complements the theme-owned type/layout system rather than replacing it.

Read the installed imagegen skill when available and use Codex's built-in image generation tool. Discover its actual exposed name and input schema; do not assume a particular namespace, model parameter, or output-path argument. Do not substitute a text description, HTML screenshot, or stock photo for a generated screen mockup. Do not silently switch to a paid API or CLI if the built-in tool is unavailable. Explain the limitation and ask whether the user wants an available fallback or to proceed without mockups; continue read-only preparation meanwhile.

Generate each screen/viewport as a separate readable image, not a tiny panel in a contact sheet. Supply existing branding and available images as references. After the first screen establishes the visual direction, reference it in subsequent generations to keep the masthead, type, palette, controls, and spacing consistent. Request straight-on website output without device frames, perspective, presentation captions, or invented UI chrome.

Include in each prompt:

- Screen/route, state, target viewport, purpose, exact important copy, and real content density.
- Shared design choices, available font families, asset references, and intended image crops.
- Theme-owned identity decisions and how the layout works with ordinary or absent editorial imagery; do not let matching art supply the entire visual personality.
- Section order, relative dimensions, type hierarchy, alignments, overlaps, and mobile rearrangement.
- Native editable WordPress content and actual working controls, without made-up product functionality.

Inspect every generated image. Repair inconsistent shared elements, illegible controls, omitted sections, and impossible layouts before selecting it. Preserve the user's chosen references; never label an agent-selected image user-approved. Present the set, then proceed under the existing implementation request unless the user asked for an approval checkpoint. Avoid an unrequested approval loop.

Keep the selected images and a small screen inventory in the workspace, with screen/state, viewport, image path, destination, shared-template mapping, and implementation status. Use returned local image paths when available; do not invent paths or download remote output to bypass display restrictions. Follow the image tool's asset-handling rules. Large mockup files need not enter the plugin package or Git history unless requested.

## Pass The Fundamentals Gate

Use [the spacing method](spacing.md) to define and inspect common insets, group proximity, reading rhythm, and major transitions. Resolve those relationships in a representative home/article proof before expanding all screens. Reject phone mockups that simply shrink desktop spacing; measure actual browser gaps and compare visible alignment, not only overflow.

### Marge Review Checkpoints

For new themes and substantial visual redesigns, discover and load the installed Marge skill alongside Impeccable. Use one independent critique-only reviewer when subagents are available. Give that reviewer the user brief, the complete desktop/mobile mockup inventory, and actual images without the designer's preferred verdict. Review every distinct screen and relevant state before implementation, not only the homepage. Ask for concrete issues in hierarchy, typography, reading rhythm, personality with ordinary media, shared-element consistency, and mobile composition. Batch the review, repair material findings, and use at most one confirmation pass rather than an open-ended polishing loop.

After implementation, reuse the reviewer with selected mockups and actual matching browser screenshots for every distinct screen/state. Check fidelity and usability separately, record necessary accessible or dynamic-content adaptations, and fix material discrepancies before claiming completion. Mockup review does not establish working controls or accessibility. Keep review evidence with the authorized theme, not as unrelated plugin documentation. If Marge or independent-agent tools are unavailable, disclose it, perform the same bounded checks locally, and label the result a self-review rather than claiming Marge reviewed it. Routine copy edits and nonvisual repairs do not require these checkpoints.

Apply this gate before selecting a mockup and again on the rendered site. A compelling image is not proof of readable typography or usable UI. Correct inaccessible mockup choices rather than faithfully reproducing them; record the adaptation. These checks apply to the requested surfaces, not an excuse to redesign unrelated pages.

- **Type roles:** Define display, heading, body, metadata, and control styles in the destination's Global Styles where supported. Start with one or two families and a small consistent scale. Choose heading levels by document structure, not desired size; normally use one main H1 per page and a logical outline. A large shared masthead must not become every page's main heading.
- **Reading:** As design starting points, use roughly 16-20 CSS px body text (often 18-20 for articles), 1.45-1.7 line height, and 45-75 characters per line. These are defaults, not WCAG thresholds or a reason to override an established readable design. Inspect actual fonts and real paragraphs. Keep metadata comfortably legible; avoid condensed faces, long uppercase passages, tight tracking, and justified text for sustained reading. Reserve Fit Text for short display copy, never body text, navigation, or form labels. Mobile needs reflow, not a scaled-down desktop page.
- **Contrast:** Measure actual foreground/background pairs, including text over images and hover/focus states. WCAG AA requires 4.5:1 for ordinary text, 3:1 for large text (at least 24 CSS px regular or about 18.7 CSS px bold), and 3:1 for necessary visual control/state indicators against adjacent colors. Decorative brand inks can remain bright while text uses a darker token. Grain and artwork must not interfere with reading. Never rely on color alone for links, errors, or selection.
- **Controls:** Use links for destinations and buttons for actions, with clear accessible names and visible labels for inputs; placeholders do not replace labels. Preserve native WordPress navigation/search behavior. Provide visible keyboard focus and a usable skip link for site templates. Check focus order, menu open/close, Escape, and focus return; modal navigation must not expose background controls to keyboard focus. Aim for 44 by 44 CSS px touch targets; WCAG 2.2 AA's 24 by 24 minimum has exceptions, so do not mislabel the larger design goal as a universal requirement. Exercise applicable active, error, empty, and disabled states without inventing unnecessary UI.
- **Spacing and alignment:** Use a small spacing scale, common container insets, consistent control heights, and deliberate relationships between labels and content. Verify the rendered logo, type, and buttons, not just their wrappers. Preserve meaningful asymmetry; fix accidental misalignment through native layout before adding offsets. Do not hide real content to reproduce a shorter mockup.
- **Resilience:** Check 320 CSS px reflow, 200% text enlargement, long titles/labels, and loaded/fallback fonts. Ordinary reading pages must not require horizontal scrolling. Test text-spacing overrides (line height 1.5, paragraph spacing 2em, letter spacing .12em, word spacing .16em) for clipping or lost functionality; these are user-override tests, not prescribed visual defaults. Keep content order meaningful without visual positioning. Respect reduced-motion preferences when adding animation.

For each distinct template family, keep a compact evidence row with viewport, body font/size/line height and reading width, heading outline, measured text/control contrast, keyboard/menu result, and screenshot. Shared header/footer checks can be reused across routes unless context changes them. An automated accessibility scan supplements manual keyboard and visual checks; it cannot prove accessibility conformance. Fix failures and explicitly label untested checks. Routine copy edits only need affected checks, not another full audit.

Standards: [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html), [target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), and [text spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html). Keep typographic taste recommendations distinct from accessibility requirements.

## Build The Selected Design

Translate the target into native Canvas geometry and WordPress blocks: headline proportions and wrapping, content widths, grid gaps, image crops, stacking, rotation, whitespace, and full-page rhythm. Record these concrete visual decisions before implementing. Resolve the real fonts and separate art assets needed for the target; a generated mockup does not supply usable font files or individual media assets.

The mockup is a specification, not a page background. Never ship a flattened screenshot, rasterized headings, fake controls, or hardcoded copies of dynamic post content. Isolated-pattern image placeholders remain native placeholders; mockup imagery is not permission to silently add production media. Preserve current authoring permissions and native parent/ancestor rules.

Do not silently replace a distinctive composition with a simpler generic layout. If an actual Canvas limitation prevents a required detail, identify it with evidence and follow the assigned implementation boundary. When engine work is authorized, fix and test the capability; otherwise report the blocked detail. Accessible focus, readable text, and real dynamic content remain required. Explain any necessary adaptation rather than claiming it is an exact match.

## Prove Fidelity In The Browser

Capture each implemented screen and state at the same viewport as its selected mockup, after fonts and images load. Use Codex's available browser or Playwright tools and inspect the actual screenshots, not just DOM dimensions. Compare the complete page and full-resolution details side by side; include the footer and neighboring sections. Also test an intermediate width and narrow overflow behavior.

Check hierarchy, type proportions, line breaks, image placement/crops, layout density, spacing, alignment, layered relationships, and repeated elements. Match material visual details, not merely palette or rough section order. Open menus and exercise forms, links, search, and pagination; a correct static screenshot is not proof of interaction quality.

For shared headers, rows, and other alignment-sensitive compositions, name the intended relationship before changing it: common baseline, vertical center, equal inset, or centering within a specific container. Do not center intentionally asymmetric designs. Measure rendered bounds after fonts load, including the actual logo, text, and controls rather than only their Canvas wrappers. Compare centers with `top + height / 2` (or `left + width / 2`) relative to that container; investigate unexplained differences over roughly 1 CSS pixel for elements intended to share a geometric center. Baseline alignment and optical balance still require screenshot inspection: different font metrics or asymmetric artwork can look wrong despite equal boxes. Prefer native Row/Stack alignment and shared spacing; do not hide a structural error with per-viewport offsets.

Repeat the alignment check at desktop, intermediate, and narrow widths, just above and below relevant layout breakpoints, and after resizing back to desktop. Exercise expanded search and open navigation. Check longer real headings/navigation labels, 200% browser zoom, and delayed font/image loading for clipping, overlap, or lost controls. Keep these probes transient or in isolated fixtures; do not overwrite the user's content. Fit Text needs both a visual check for oversized letter stacks and a stable layout after repeated resizing; correct attributes alone are not evidence that it works.

Record concrete differences, fix the largest ones, and recapture affected screens. Recheck the whole composition after material changes. Do not regenerate the mockup to resemble an easier implementation or quietly downgrade the target. Keep deliberate target revisions separate and explain why they changed. A pixel-difference score may assist but cannot replace visual judgment; font rendering and genuine dynamic content need contextual assessment.

Finish only when there are no known material mismatches and the native editor remains usable, or explicitly report what is blocked. Never promise or claim pixel-perfect implementation without evidence. Report fidelity separately from functional tests, with mockup and final screenshot paths plus any remaining deviations. Tests passing is not design signoff.

For a whole-site delivery, keep a compact evidence record mapping representative routes/states to viewport checks, screenshots, interaction results, and editor save/reload results. Mark untested items explicitly. When an independent visual review is requested, give the reviewer the mockups and actual screenshots, ask for concrete discrepancies, then repair and recapture before closing findings. Release readiness also needs keyboard/focus, contrast, meaningful reading order, and real-device/assistive-technology checks appropriate to the requested scope; do not imply those passed merely because a screenshot or automated audit passed.

For reusable theme delivery, install the actual packaged ZIP into clean disposable WordPress without demo seed or a bind-mounted theme. Verify default latest-posts and supported static-homepage paths, real navigation destinations, useful no-content states, and native branding/Global Styles customization. Demo-only page slugs must not be prerequisites for a usable default site. Activation must not silently import demo content. Check the current [WordPress.org theme requirements](https://make.wordpress.org/themes/handbook/review/required/) and appropriate Theme Check/static checks before claiming submission readiness, including package hygiene, compatible resource licenses/credits, translations, secure code, and keyboard/skip-link behavior. Preserve supplied Canvas distribution decisions; verify the authorized runtime rather than reopening an already settled product choice. Record design clearance, functional tests, fresh-install/customization evidence, and directory eligibility separately.
