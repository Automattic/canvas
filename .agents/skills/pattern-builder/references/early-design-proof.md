# Early Design Proof

For a new reusable theme or substantial redesign, read this after the user selects a concept and before generating the entire screen family. This is a small native WordPress feasibility and design proof, not permission to build the whole theme early. Routine copy edits and narrow repairs do not restart this workflow.

## Keep The Proof Small And Real

Use the selected Imagegen concept as the visual target. In an authorized isolated WordPress fixture, compose one representative home, one approximately 600-word article, and the mobile menu, using Canvas and native dynamic blocks. Reuse the same header/footer, actual candidate fonts, and ordinary existing media. Map repeated routes to templates; do not add a complete theme catalog or generate fresh photos for stress tests.

Inspect 320/390px, one intermediate width, and wide desktop in one batch. A plain HTML font specimen may supplement reading inspection but cannot establish native layout, controls, or editor behavior. If the native runtime is unavailable, report that proof as unverified, continue permitted source preparation, and do not expand paid screen generation under a claim that the gate passed.

## Seven Decisions To Prove

Apply [the compelling-design gate](compelling-design.md) to this proof as well: record the selected editorial idea and recognizable relationships, then judge whether the real native composition carries them with ordinary content. An early proof that is functional but generic does not clear the appeal judgment merely because its geometry passes.

1. **Typography relationships.** Record display, heading, body, metadata, caption, and control roles, including fonts/available weights, sizes, leading, and intended measures. Inspect them together with real paragraphs, a long title, links, a subheading, list, quote, and caption. Resolve heading hierarchy and verify font licensing. Judge readable proportions rather than merely checking that fonts loaded. Do not rasterize text or shrink reading text to fit a screenshot.
2. **Shared components.** Establish authoritative desktop/phone header, footer, search, navigation, and post-entry compositions. Record their native editing surfaces, spacing owners, and applicable states. Every later route references these targets. Document purposeful compact-header or reading-width variants rather than allowing each generation to invent new chrome.
3. **Phone composition.** Define source reading order, stacking, common gutters, title wrapping, media behavior, and control arrangement deliberately. Inspect the open native menu, close/Escape/focus return, visible search labels, and usable targets. A desktop page shrunk to phone width is a failed proof even without horizontal overflow. For long mockups use ordered readable continuations; do not squeeze the whole article into a tiny image.
4. **Content resilience.** Use a compact fixture with a long site name/title, unequal excerpt lengths, ordinary portrait/landscape photos, actual missing featured images, and a sparse query. Reuse home/article compositions and a small query-state probe rather than building another route family. Missing media must remove its space and later content/footer must still clear growing text. DOM replacement is a supplementary visual probe, not proof of actual absent-media data. Restore only the disposable fixture.
5. **Artwork discipline.** Write a small artwork plan: each asset's purpose, placement, crop, maximum visual prominence, repetition policy, phone adaptation, and when it is omitted. Generate bespoke raster artwork with built-in Imagegen and keep it separate from editable text/UI and editorial photos. Reuse clean assets already generated for the proof during later mockups and production rather than generating them again. Verify alpha/crops/credits, and inspect a no-photo state. If repeated art overwhelms prose, change its placement/frequency rather than generating more decoration.
6. **Native editing quality.** In the fixture, change site branding, a relevant font, a palette color, a spacing setting, and a header/footer or post-entry setting through their intended WordPress controls. Batch safe changes, but verify the effect of each and record any untested control. Save, reopen, verify valid blocks, and inspect the frontend. Record which native control owns each change. A successful backend write alone is not an editor test. Keep user Global Styles authoritative; record verified CSS exceptions instead of overriding user choices to preserve demo pixels.
7. **Evidence-based approval.** Record separate judgments for appeal, mockup fidelity, functional behavior, native editability, and release eligibility. Give an independent reviewer the selected concept, actual proof screenshots, fixtures, and checks without a preferred verdict. The early gate clears only the shared design and native feasibility for screen expansion; it is not complete-theme, accessibility, or WordPress.org approval.

## Expansion Gate And Budget

Before full screen generation, record the shared type/spacing/component contract, artwork plan, proof screenshots, content fixtures and editor results. Proceed only when no material reading, spacing, phone, content-growth, or native-editing blocker remains. Correct findings in one batch and confirm the affected proof once. If material issues remain, show them honestly and seek the user's decision on additional work rather than silently spending on every route.

Then generate every distinct desktop/mobile screen and applicable state in the chosen direction using the authoritative shared targets. Complete the independent full-mockup review before production theme implementation. The limited native proof is the explicit exception to the mockup-first production rule, not a loophole for implementing all templates before review.

Reuse valid evidence, one small fixture and one reviewer; do not spawn an agent or generate an image for each individual check. Existing failing mocks remain marked unapproved until corrected; updating this skill does not retroactively approve them.

## Evidence Record

Keep a compact record alongside the theme, not inside unrelated plugin documentation:

| Judgment | Evidence required | What it does not establish |
| --- | --- | --- |
| Appeal | Independent visual critique of actual proof | Usability or audience consensus |
| Fidelity | Comparison with selected target; explained native adaptations | Working controls |
| Function | Exercised routes, queries, menu/search, keyboard and content growth | All controls or accessibility conformance |
| Editability | Native control changes, save/reopen, valid blocks, frontend parity | Clean packaged installation |
| Release | Actual ZIP on clean WordPress, resource credits, applicable current checks | Directory acceptance or publishing authorization |

Use pass, fail, unverified or not applicable for each judgment, with target/version, viewport, evidence path and remaining issue. A pass is scoped to recorded evidence. Collect actual visible spacing distances as well as computed styles; distinguish actual browser zoom/RTL language tests from simulations.
